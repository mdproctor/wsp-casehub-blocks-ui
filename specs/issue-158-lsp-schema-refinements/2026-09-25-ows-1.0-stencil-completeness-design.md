# OWS 1.0 Stencil Completeness

**Issue:** #172
**Branch:** issue-158-lsp-schema-refinements
**Date:** 2026-09-25

## Overview

Complete the OWS 1.0 task type coverage in graph-stencil-swf. The SDK
defines 12 task types via `GraphNodeType`. We have stencils for 7 (Call,
Set, Switch, For, Raise, Try, TryCatch). This spec adds the remaining 6:
Do, Emit, Fork, Listen, Run, Wait.

Also upgrades `@openworkflowspec/sdk` from 0.0.1 to 1.0.3-alpha8 and
updates example YAML to `dsl: '1.0.3'` syntax.

## Task Type Classification

Per OWS 1.0 DSL reference and D8:

| Type | Category | OWS semantics | Has children? |
|------|----------|---------------|---------------|
| Do | Container | Sequential sub-task group | Yes — inline `do: TaskList` |
| Fork | Container | Parallel concurrent branches | Yes — `fork.branches: map[string, task]` |
| Emit | Leaf | Publish event to broker | No |
| Listen | Leaf | Await external events | No |
| Run | Leaf | Execute container/script/shell/workflow | No |
| Wait | Leaf | Pause for duration | No |

All 6 support `then` for chaining (OWS 1.0 default: `"continue"`).
None are terminal — even `wait` proceeds after the duration.

## Container Stencils

### Do

Sequential sub-task container. The simplest container — a named scope
around a task list. The SDK produces entry/exit synthetic nodes inside
the `do` sub-graph.

**Render:** Compact header (same style as `for`/`try`). Icon: `📋`
(clipboard/list). Label from task name or "Do".

**Grammar:** Same connection pattern as `for` — inbound from any flow
task, outbound max 1 to any flow task.

**Layout:** The existing stack-column layout handles containers via
`parentId`. Children render sequentially inside the container box.
`do` nodes must be added to the `containerTypes` set in
`swf-diagram.ts` for container styling (orange border + grey
background).

**Edge visibility:** Internal edges inside `do` containers should be
shown (sequential body flow), same as `for`. This contrasts with
`try`/`try-catch` which hide internal edges (structural, not
sequential).

### Fork

Parallel branch container. Each branch is a named task (which could
itself be a `do` with sub-tasks). The `compete` flag controls whether
branches race (first wins) or join (all complete).

**Render:** Compact header with `compete` badge. Icon: `🔀` (parallel
arrows). Badge shows "race" when `compete: true`, hidden when false
(default). Label from task name or "Fork".

**Grammar:** Same inbound as other containers. Outbound max 1 (the
convergence edge after all branches complete).

**Layout:** Fork branches render as side-by-side columns (D9), reusing
the stack-column algorithm's column tree logic. The SDK produces child
nodes for each branch with `parentId` pointing to the fork node.

**Edge visibility:** Internal edges within fork containers are hidden
(structural — branches are independent parallel paths, not a sequence).
The layout positions branches side-by-side; edges between them would be
misleading.

**Container styling:** Same as for/try — orange border + grey
background. This is applied by the `containerTypes` set in
`swf-diagram.ts`.

## Leaf Stencils

All four follow the Call/Set/Raise card pattern: bordered box with icon,
label, and subtitle.

### Emit

Publish events to event brokers (CloudEvents format).

**Render:** Card with purple accent (#7c3aed). Icon: `📡`. Subtitle:
event type from `emit.event.with.type` if present.

**Grammar:** Normal flow — inbound from any flow task, outbound max 1
to any flow task.

### Listen

Await and react to external events. Blocks until the configured event
consumption strategy is satisfied.

**Render:** Card with teal accent (#0d9488). Icon: `📻` (antenna).
Subtitle: consumption strategy label — "all N events", "any of N
events", or "one event" derived from `listen.to` structure.

**Grammar:** Normal flow — same as emit.

### Run

Execute external containers, shell commands, scripts, or sub-workflows.

**Render:** Card with green accent (#059669). Icon: `⚙️` (gear).
Subtitle: sub-type indicator derived from which property is set —
"container: {image}", "shell: {command}", "script: {language}", or
"workflow: {name}".

**Grammar:** Normal flow — same as emit.

### Wait

Pause execution for a specified duration.

**Render:** Card with slate accent (#475569). Icon: `⏳` (hourglass).
Subtitle: formatted duration from `wait` property (e.g. "30s", "5m",
"1h 30m"). Falls back to "wait" if duration is complex.

**Grammar:** Normal flow — same as emit.

## Grammar Updates

### New type connections

All existing grammars must add the 6 new types to their
`allowedFrom`/`allowedTo` lists. The principle: any non-terminal flow
task can connect to/from any other non-terminal flow task.

**Types that appear in `allowedFrom` (can receive incoming edges):**
`swf-call`, `swf-set`, `swf-switch`, `swf-for`, `swf-do`, `swf-fork`,
`swf-emit`, `swf-listen`, `swf-run`, `swf-wait`, `swf-entry`,
`swf-start`

**Types that appear in `allowedTo` (can send outgoing edges):**
`swf-call`, `swf-set`, `swf-switch`, `swf-for`, `swf-do`, `swf-fork`,
`swf-emit`, `swf-listen`, `swf-run`, `swf-wait`, `swf-raise`,
`swf-exit`, `swf-end`

Note: `raise` stays outbound-0 (no outgoing connections) since it
throws an error. `raise` appears only in `allowedTo` (can be a target).

Each existing stencil grammar needs updating:
- `callGrammar` — add 6 types to both allowedFrom and allowedTo
- `setGrammar` — same
- `switchGrammar` — same
- `forGrammar` — same
- `raiseGrammar` — add 6 types to allowedFrom only (outbound stays 0)
- `tryGrammar` — add 6 types to both
- `tryCatchGrammar` — add 6 types to both
- `startGrammar` — add 6 types to allowedTo
- `endGrammar` — add 6 types to allowedFrom
- `entryGrammar` — add 6 types to allowedTo
- `exitGrammar` — add 6 types to allowedFrom

### Grammar constants

The grammar lists are becoming long and repetitive. Extract two shared
constants:

```typescript
const FLOW_SOURCES = [
  'swf-call', 'swf-set', 'swf-switch', 'swf-for', 'swf-do', 'swf-fork',
  'swf-emit', 'swf-listen', 'swf-run', 'swf-wait', 'swf-entry', 'swf-start',
];

const FLOW_TARGETS = [
  'swf-call', 'swf-set', 'swf-switch', 'swf-for', 'swf-do', 'swf-fork',
  'swf-emit', 'swf-listen', 'swf-run', 'swf-wait', 'swf-raise', 'swf-exit', 'swf-end',
];
```

Each grammar references these constants instead of inline arrays.
Boundary nodes (`start`, `end`, `entry`, `exit`) and `raise` have
custom subsets.

## SDK Upgrade

Pin `@openworkflowspec/sdk` to `1.0.3-alpha8` in
`packages/graph-stencil-swf/package.json`. Currently `"*"` resolving
to 0.0.1.

The `buildFlatGraph(workflow, removePorts?)` API signature is unchanged
between 0.0.1 and 1.0.3-alpha8. The `GraphNodeType` enum already
includes all 12 types in 0.0.1. The `Specification.Workflow` type is
structurally compatible.

Risk: low. The SDK is consumed only in `swf-adapter.ts` via
`buildFlatGraph`. No other API surfaces are used.

Add `'swf-fork'` to the list of parent types that hide internal edges
(alongside `swf-try` and `swf-try-catch`). `swf-do` keeps internal
edges visible (like `swf-for`).

### Handle visibility (_computeFilteredNodes)

Add `'swf-do'` and `'swf-fork'` to the inner-structural check so
nested container nodes hide handles appropriately.
